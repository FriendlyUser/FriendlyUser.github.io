Calling C and C++ code from Go with cgo and SWIG

Jan 17, 2024Go
  • #c
  • #go
  • #cpp

Sometimes the library you need only exists in C or C++, or you already have a C++ codebase and want a Go service to use it. Go gives you two routes: cgo, which is built into the Go toolchain and calls C directly, and SWIG, which generates Go bindings for C and C++ code. cgo only understands C, so for C++ you either put a small C interface in front of it or let SWIG generate one.

Both need a C/C++ compiler (gcc or clang) on your PATH.

cgo: calling C directly

Section titled “cgo: calling C directly”

Put C code in a comment immediately above import "C" (no blank line in between). That comment is the preamble: cgo compiles it and makes its functions, types and macros available as C.name.

A few things to know:

  • CGO_ENABLED defaults to 1 for native builds when a C compiler is found. Since Go 1.20 it defaults to 0 if no C toolchain is on the PATH, and you’ll need to set it to 1 explicitly when cross-compiling with a cross C compiler.
  • C types appear as C.int, C.char, C.double and so on. Convert explicitly (int(sum), C.int(x)).
  • C.CString copies a Go string into C memory that Go’s garbage collector doesn’t manage. Free it with C.free, which needs stdlib.h in the preamble.
  • C’s stdout is buffered separately from Go’s, so output from printf can go missing when it’s piped and the program exits. The fflush call avoids that.
  • Each call across the boundary costs far more than a normal Go function call, so cgo pays off for chunky work (decode an image, run a query), not for calling a tiny C function in a tight loop.

cgo with C++: an extern "C" shim

Section titled “cgo with C++: an extern "C" shim”

SWIG: generating the bindings

Section titled “SWIG: generating the bindings”

Writing shims by hand gets tedious for a large C++ API. SWIG reads your headers and generates both the C wrapper and the Go code. The go tool has built-in SWIG support: if a package directory contains a .swigcxx file (or .swig for C), go build runs SWIG and compiles the result. You don’t run swig or g++ yourself.

Which one to use

Section titled “Which one to use”
  • A few C functions: cgo with a preamble or a header is simplest.
  • A small C++ surface: an extern "C" shim keeps you in plain cgo and keeps the boundary explicit.
  • A large C++ API you don’t want to wrap by hand: SWIG, accepting generated code you’ll sometimes need to read when things go wrong.

In every case cgo is in play, so builds need a C toolchain, cross-compiling gets harder, and you lose Go’s fully static, single-toolchain builds. If a pure-Go library does the job, it’s usually worth that trade.
