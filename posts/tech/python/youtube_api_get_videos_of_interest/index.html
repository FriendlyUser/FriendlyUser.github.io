Finding new YouTube videos of interest with the YouTube Data API in Python

May 2, 2024Python
  • #python
  • #youtube

This is a walkthrough of the YouTube part of my media_nlp project. It checks a list of investing channels once a day, picks out new videos, runs keyword matching over the title and description, and emails me a table of what it found.

You need a YouTube Data API v3 key from the Google Cloud console, exposed to the script as YOUTUBE_API_KEY. Reading public video data only needs an API key; OAuth 2.0 is only required for acting on a user’s account (uploading, managing playlists, and so on).

Fetching recent videos for a channel

Section titled “Fetching recent videos for a channel”

The project calls the search endpoint, filtered to one channel and to videos published in the last day. This is a cleaned-up version of the project’s get_videos.py:

search.list is the expensive call to lean on. The quota docs give projects a default of 10,000 units a day for most endpoints, but ration search.list separately (100 calls a day by default at the time of writing), and the search docs warn that order=date results can be delayed or incomplete. For “latest uploads from channel X”, Google recommends reading the channel’s uploads playlist instead: get its ID from channels.list (part=contentDetails, contentDetails.relatedPlaylists.uploads), then page through playlistItems.list.

The main loop

Section titled “The main loop”

Channels are grouped into reports by YAML config files. For each new video, YTNLP (a class in the project) generates a transcript report and matches the title and description against a list of phrases. This is a trimmed excerpt of scripts/main.py; get_config and YTNLP live in the project’s lib package.

The excerpt stops before the reporting step, where email_channel_data is rendered and sent.

An earlier version checked if video_id in yt_df, which never matches: yt_df is a list of dicts, not a list of IDs, so already-processed videos were reprocessed. Building seen_ids once fixes that. The remaining weak spot is the JSON file as a database; it grows every day and is rewritten in full, so SQLite would be a better fit.

Render it with the list built in the main loop (here the template is saved as lib/email_template.html), then send it through Mailjet’s Send API v3.1. Note that v3.1 expects the message inside a Messages list:

Turn on autoescaping: video titles and descriptions are third-party text going straight into HTML. The sender address must be one you’ve verified in Mailjet, or the send is rejected.
