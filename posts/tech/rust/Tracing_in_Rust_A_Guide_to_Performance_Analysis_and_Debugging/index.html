Getting started with the tracing crate in Rust: spans, events and tokio-console

Apr 22, 2023Rust
  • #rust

tracing is the Tokio project’s library for structured, contextual diagnostics. Where a plain logger records isolated lines, tracing records spans (a period of time, like a function call or a request) and events (a point in time inside a span), so every log line knows which request or task it belongs to. You instrument your code once, then choose at startup what to do with the data: print it, filter it, time it, or ship it to another tool.

Setup

Section titled “Setup”

tracing provides the macros you put in your code; a subscriber decides what happens to the data. tracing-subscriber provides the usual one.

(The crate name uses a hyphen; you refer to it as tracing_subscriber in code. This post was checked against tracing 0.1.44 and tracing-subscriber 0.3.23.)

fmt::init() installs a formatting subscriber globally (it panics if one is already installed). With the default features it prints events at INFO and above; if you enable the env-filter feature it reads the filter from RUST_LOG instead, e.g. RUST_LOG=debug cargo run.

#[instrument] wraps the function body in a span named after the function and records its arguments as fields using their Debug impls, so the event above prints with some_function{id=42} as context. Use #[instrument(skip(big_arg))] for arguments that are large or don’t implement Debug.

Spans and events

Section titled “Spans and events”
  • A span has a start and end, can carry fields, and nests inside other spans.
  • An event is a single point in time. It is recorded inside whatever span is current.

Create a span manually with span! (or the level shortcuts info_span!, debug_span!, …) and enter it:

Events take structured fields (entries = 3) in addition to the message, which is what makes the output filterable and machine-readable (tracing_subscriber::fmt().json() with the json feature).

Caution

Don’t hold the guard from span.enter() across an .await. When the task yields, the span stays “entered” on that thread and gets attached to unrelated work. For async code use #[instrument] on the async fn, or future.instrument(span) from the tracing::Instrument trait.

Timing spans

Section titled “Timing spans”

For quick performance checks you don’t need extra tools. Ask the fmt subscriber to log when spans close; it adds time.busy (time spent inside the span) and time.idle (time the span existed but wasn’t entered):

The idle time is mostly useful for async code, where it shows how long a future spent waiting rather than running.

Section titled “Inspecting async tasks with tokio-console”
